# Decisiones y ambigüedades

1. **Fecha de autorización frente a fecha de factura.** Los códigos usan el día de solicitud en Guatemala (UTC-6), como indica el enunciado. Los reportes agrupan por la fecha de TIEMPO. Cargar una factura de 2025 hoy no genera un código de 2025.
2. **Algoritmo del NIT.** Se excluye el verificador final; los dígitos de la base se multiplican de derecha a izquierda por 2, 3, etc. El resultado `(11 - suma % 11) % 11` se compara con el verificador; 10 representa K. Se admiten 1 a 20 dígitos de base. Los NIT se mantienen como cadenas para no perder ceros iniciales ni desbordar con bases largas.
3. **Ejemplo inválido del PDF.** El ejemplo `5123456` no cumple el algoritmo; no se introduce una excepción para aceptarlo. Las pruebas originales usan `5123453` como válido y `5123456` como inválido.
4. **Tiempo tolerante.** Una expresión regular extrae día/mes/año y hora/minuto; DateTime comprueba calendario y límites. Se ignoran lugares, `hrs.` y texto decorativo. Se admiten día, mes u hora de un dígito según los casos de borde del ZIP. La hora es obligatoria.
5. **Montos.** Se usa decimal. IVA = redondear(VALOR * 0.12, 2, AwayFromZero). TOTAL se compara con VALOR + IVA recibido; el caso E07 produce error de IVA y no de TOTAL. Se aceptan números con cero, una o dos posiciones decimales: JSON no conserva una diferencia semántica entre 100 y 100.00. No se aceptan montos como texto, negativos, VALOR/TOTAL cero o fracciones monetarias adicionales.
6. **Referencias.** Son obligatorias y de máximo 40 caracteres. Se comparan exactamente, distinguiendo mayúsculas y minúsculas. Una autorización reserva la referencia globalmente. Un rechazo no la reserva, por lo que se puede corregir y reenviar. Las duplicadas del mismo lote se detectan inmediatamente.
7. **Descartes.** Campos ausentes o mal tipados, fecha inválida, referencia fuera del límite o monto fuera del formato se registran como descartes. Se conserva posición, referencia, motivo y momento de recepción. No se inventa una fecha de factura para agruparlos en el reporte diario.
8. **Lotes.** El contenedor debe ser homogéneo. JSON malformado, arreglos vacíos y mezcla RTU/facturas se rechazan antes de modificar el estado. Los errores de negocio son por factura y permiten seguir procesando las otras filas.
9. **Correlativo y concurrencia.** Un bloqueo cubre la lectura, validación, asignación y escritura. Se conserva un contador por día y se usa un archivo de bloqueo con FileShare.None para impedir dos procesos escritores. Llegar a 99,999,999 autorizaciones en un día rechaza el lote completo. Inicializar borra también los contadores, conforme al estado inicial solicitado.
10. **Persistencia.** Una copia de trabajo se serializa a un archivo temporal, se vacía a disco y reemplaza el estado. Solo entonces se cambia la copia en memoria y se confirma la respuesta. Un estado ilegible detiene el arranque; nunca se vacía automáticamente. El diseño está destinado a un proceso API y un archivo local, no a escritores distribuidos.
11. **Estadísticas.** Emisores y receptores distintos del reporte diario incluyen los NIT de los intentos parseables, aunque se rechacen. Cada categoría de error cuenta todas sus apariciones; aprobadas + rechazadas equivale a recibidas parseables.
12. **Tecnología.** Se utiliza .NET 10 instalado en el entorno, ASP.NET Core, Razor Pages, System.Text.Json y tipos de C#. Las abstracciones IRepositorio, IReloj y EstadoSistema encapsulan la interacción con los datos. Los PDF y SVG se generan en C# sin librerías externas.

Estos criterios son explícitos para que puedan contrastarse con aclaraciones posteriores del auxiliar. Las pruebas y los archivos de entrada originales permanecen sin modificaciones.
